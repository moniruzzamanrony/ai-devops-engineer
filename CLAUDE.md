## Project Overview
`ai-devops-engineer` ("Devops AI" / "Rony CLI") is a single-binary Python Typer CLI that
drives an LLM-powered DevOps assistant. The user picks an intent (e.g. "Server setup and
deployment"), the CLI gathers repo + server + domain inputs, then asks a Hugging Face-hosted
model to generate a JSON array of idempotent shell commands (mostly `sshpass ... ssh ...`),
parses them, runs them locally, captures errors, and loops back to the model for fixes.

## Coding Conventions

### CLI (Python / Typer)
- **Entry point**: `main.py` imports `app` from `app.cli` and calls it. `app/cli.py` registers each command function (`start`, `deploy`, `config`, `version`) via `app.command()(fn)` — one function per file under `app/commands/`.
- **Imports**: absolute imports rooted at `app.` (e.g. `from app.services.ai_service import ask_devops`). No relative imports observed.
- **Folder roles** (`app/`):
  - `commands/` — Typer command handlers (one file per command).
  - `core/config.py` — env loading via `python-dotenv`, HF API constants, server-credential lookups.
  - `config/hugging_face_client.py` — single function `call_hf(prompt)` that POSTs to HF and returns the JSON dict.
  - `services/ai_service.py` — main orchestration: `ask_devops(prompt)` calls HF, parses, queues commands into a `deque`, runs each via `run_command`, collects errors, and recurses with `generate_error_fix_prompt` if any errors remain.
  - `tools/` — low-level helpers: `run_cmd.run_command` (subprocess wrapper that filters known-noise stderr lines), `input_validator.get_non_empty_input`, `temp_credential` (JSON read/write/remove for `temp_credential.json`).
  - `utils/prompt_text.py` — banner + all LLM prompt templates (`generate_deployment_prompt`, `generate_result_analysis_prompt`, `generate_error_fix_prompt`, `get_valid_json_response`). Prompts read runtime values via `temp_credential.get_value(...)`.
  - `dto/dev_ops_request.py` — `DevOpsRequest` Pydantic model (defined but not yet wired into the CLI flow).
- **Input handling**: interactive `input()` calls inside command bodies, validated with either inline `is_empty` checks (in `start.py`) or `get_non_empty_input` (in `config.py`). Several inputs in `start.py` are overwritten with hard-coded test values immediately after being read (`repo_link = '...rent-tech-api.git'`, `server_name = 'rent_tech'`, `domain = 'mapmark.live'`) — looks like dev scaffolding, not intended for release.
- **State between steps**: persisted to `temp_credential.json` at the cwd via `app/tools/temp_credential.py`. Prompt templates read it back with `get_value(...)`.
- **Command execution**: `run_command` uses `subprocess.Popen(..., shell=True)` and returns `{"output", "error"}`. Errors are filtered through a noise-keyword blocklist before being surfaced.
- **AI-instruction parsing**: `parse_ai_instructions` (in `ai_service.py`) strips ```` ```json ```` fences, fixes invalid backslash escapes, tries direct `json.loads`, falls back to bracket-substring extraction with trailing-comma cleanup, and finally re-prompts the model up to `max_retries=3` times for valid JSON.
- **Logging**: ad-hoc `log(message, level, indent)` function in `ai_service.py` that prefixes lines with emoji + timestamp + level. Not using `logging` stdlib.
- **Error handling**: mostly `try/except Exception as e` with a logged message; failures inside the command loop log + continue, while an invalid command name (`shutil.which` miss) calls `sys.exit(1)`.
- **No tests** present in the repo.

## Known Rough Edges (be aware before refactoring)
- `app/commands/config.py:62` runs `update_env("DB_NAME", "my_database")` at **import time** — every `import` of this module rewrites `.env`. Almost certainly a bug.
- `app/commands/start.py` hard-codes test values right after each `input(...)` (repo link, server name, domain). These overwrite user input.
- `app/services/ai_service.py:105` uses `is not ""` which is a Python identity check, not equality — `!= ""` is what's meant.
- `ask_devops` recurses on retry / on error-fix prompts; deep retries can blow the stack and `error_block` is a **module-level** list that accumulates across calls.
- `run_command` runs `shell=True` against AI-generated strings. `is_valid_command` only checks that the first token resolves via `shutil.which`, which is not a security boundary. Treat any expansion of this surface area carefully.

## How to Work on This Project
- Active work is on the `cli-v1` branch — keep changes scoped to that branch unless told otherwise.
- When touching deployment behavior, remember three layers move together: the **prompt template** in `app/utils/prompt_text.py`, the **parser/executor** in `app/services/ai_service.py`, and the **inputs collected** in `app/commands/start.py`.
- When adding a new CLI command: create `app/commands/<name>.py` exposing a single function with a docstring (Typer uses it as help text), then register it in `app/cli.py` with `app.command()(<name>)`.
- Prefer editing existing patterns over introducing new ones. If a refactor is needed (e.g. replacing the recursive retry loop, or fixing the import-time `update_env` call), call it out explicitly before doing it.
- No automated tests exist — verify changes by running `python main.py <command>` from the repo root with a populated `.env`.
